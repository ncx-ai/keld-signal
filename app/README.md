# Keld Signal — the desktop shell

A Tauri 2 app that opens a window on the daemon's own page
(`http://127.0.0.1:<port>/?secret=…`, read from `~/.keld/agent.json`). It runs
nothing, holds no credential, and makes no outbound request — see the header
comment in `src-tauri/src/main.rs` for the full design rules. It is the same
page `keld signal open` opens in a browser.

## Building

```bash
cd app
PATH="$HOME/.cargo/bin:$PATH" npx --yes @tauri-apps/cli@latest build --bundles app
```

Produces `app/src-tauri/target/release/bundle/macos/Keld Signal.app`.

## Tray icon

A status-bar icon with a two-item menu: **Open Keld Signal** (shows and
focuses the window) and **Quit** (actually exits the process). Closing the
window hides it to the tray instead of quitting — the macOS convention for a
status app (Dropbox, 1Password, Bartender all behave this way): the daemon
keeps collecting regardless of whether this window is open, so a close click
must not read as "stop everything".

The tray icon (`src-tauri/icons/tray-icon.png`) is a separate asset from the
app's own icon (`icons/icon.png`), not a shrunk copy of it. The app icon is a
coloured, full-bleed mark (dark green background, gold + white glyph) that
reads as a solid block at menu-bar size and, worse, would render as flat,
wrong-looking color swatches once marked as an NSImage *template* — macOS
recolors a template image's alpha shape per menu-bar theme (light / dark /
highlighted), and it can only do that if the RGB channel carries no meaning of
its own. `tray-icon.png` was regenerated from the app icon: the flat
background dropped, the gold+white glyph kept as solid black with the
original edges preserved as alpha, then cropped tightly to the glyph's own
bounding box (27×44, not padded to a square — the mark is naturally tall and
narrow) instead of shrinking the full square canvas. It's built with
`icon_as_template(true)` set in `main.rs`.

## Autostart ("Start at login")

Wired via the official `tauri-plugin-autostart` (a macOS LaunchAgent /
Windows registry Run key / Linux XDG autostart entry, depending on platform).
Two Tauri commands are exposed for the page to call:

- `set_autostart(enabled: bool) -> Result<(), String>`
- `get_autostart() -> Result<bool, String>`

Call them from the page via the Tauri JS API, once it detects it is running
inside this shell (`window.__TAURI__` is present only there, never in a
regular browser tab):

```js
if (window.__TAURI__) {
  const { invoke } = window.__TAURI__.core;
  await invoke("set_autostart", { enabled: true });
  const enabled = await invoke("get_autostart");
}
```

**Not wired to the page yet.** `internal/agent/ui/app.js`'s "Start at login"
toggle (D2's lane, out of scope here) renders permanently disabled today with
"This browser only, until the Keld Signal app manages startup." — see
`docs/v3/contracts.md`, point 4 under "The page's own conventions". Until D2
adds the `window.__TAURI__` detection and calls these two commands, the
toggle stays exactly as disabled as it is now; nothing about this shell makes
it do otherwise on its own.

The command names above (`set_autostart`, `get_autostart`) and their exact
signatures are the contract D2 wires against — don't rename them without
updating that lane too. They are registered via `build.rs`'s
`AppManifest::commands(&["set_autostart", "get_autostart"])`, which
autogenerates the `allow-set-autostart` / `allow-get-autostart` ACL
permissions under `permissions/autogenerated/`, granted to the main window in
`src-tauri/capabilities/default.json`. That capability also grants
`remote.urls: ["http://127.0.0.1:*"]` — required because this window loads the
daemon's page as **external/remote** content (not the bundled frontend), and
Tauri does not inject `window.__TAURI__` into remote content without an
explicit grant.

## `keld signal open` prefers the app

When `Keld Signal.app` is installed (`/Applications` or `~/Applications` on
macOS; a handful of conventional paths or `PATH` on Linux/Windows — see
`internal/cli/signalopen.go`'s `appInstallPath`), `keld signal open` launches
it instead of opening a browser tab. `keld signal open --browser` forces the
old browser-tab behaviour regardless of whether the app is installed.

## Signing the app bundle

`installers/macos/build-pkg.sh` signs every Mach-O in the **pkg payload**
(`keld`, `keld-agent`) with `sign-macho.sh` when `APPLE_DEVELOPER_ID_APP` is
set. It does **not** touch this app bundle by default — whether the desktop
app ships inside that pkg or as its own `.dmg` hasn't been decided yet, and
the default must not change the pkg's payload while that's undecided.

Two options exist today, both opt-in:

1. **Sign it via `build-pkg.sh`, without shipping it in the pkg.** Set
   `KELD_APP_BUNDLE` to the built `.app`'s path when invoking `build-pkg.sh`:
   ```bash
   APPLE_DEVELOPER_ID_APP="Developer ID Application: …" \
   KELD_APP_BUNDLE="app/src-tauri/target/release/bundle/macos/Keld Signal.app" \
   installers/macos/build-pkg.sh "$VERSION" "$STAGE" "$ARCH"
   ```
   This runs the same `sign-macho.sh` sweep against the app bundle as a
   sibling step — it never adds the bundle to `$STAGE` or the pkg payload.
   Useful for producing a signed `.app` (e.g. to zip and notarize separately,
   or wrap in a `.dmg`) using the same CI identity as the pkg build, without
   committing to a shipping decision yet.
2. **Sign it standalone**, outside `build-pkg.sh` entirely:
   ```bash
   APPLE_DEVELOPER_ID_APP="Developer ID Application: …" \
   installers/macos/sign-macho.sh "app/src-tauri/target/release/bundle/macos/Keld Signal.app"
   ```

Neither option is wired into CI yet; both are levers for whoever picks the
shipping shape (pkg-bundled vs. standalone dmg) to use without a second signing
script to write.

## Notes for whoever wires the app into distribution

- `tauri.conf.json`'s `bundle.targets` is `["app", "dmg"]` — a dmg build is
  already configured, just not produced by CI.
- The app is unsigned by default (matches the pkg's own unsigned-first
  posture); Gatekeeper will warn on an unsigned/un-notarized `.app` the same
  way it does on an un-notarized pkg.
- `KELD_HOME` is honoured (see `keld_home()` in `main.rs`) so a developer can
  point a built app at an isolated daemon for testing, exactly like the Go
  side.
