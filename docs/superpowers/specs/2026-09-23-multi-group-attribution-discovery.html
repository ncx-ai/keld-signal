Multi-Group Attribution — Discovery

Settles how Signal attributes one block to one workstream per group, not one overall A block may belong to several workstreams, even inside one group. A group counts each block once; a workstream counts every block it holds. If this is wrong, the Signal page keeps telling people a valid setup is broken. The on-device semantic pass also keeps hiding work from every group but one.

Consequences worth knowing

  • Coverage drops on org machines the moment this ships: blocks that only an Atlas workstream matched become unattributed on the page (the Today rows recompute live). They reappear as suggestions, which is where a person makes a Signal workstream for them.
  • Atlas's numbers do not move. Atlas already attributes from its own rules and the block's dimensions; neither changes.
  • Atlas's matcher suggestions keep their input without Signal knowing Atlas's definitions. Each block's project_matches still lists the Signal workstreams it matched, each with its repos and ticket key (no name, no id). Atlas can compare a person's grouping with its own — "mine has A and B, theirs has A, B and C, so suggest C" — because only Atlas holds both sides. Today Atlas's suggestion code reads only entries carrying an Atlas id; reading these by shared repos is Atlas-side follow-up work. Existing "Same as" entries keep their Atlas id and keep feeding it as they do now.
  • Signal's local ids are built from titles (p_ + slug), which is why they never go on the wire — project_matches already omits them, and that stays.

  • So the facets are renamed too. Renaming project → workstream alone would leave “workstream” with two meanings still.

The why

  • Problem: Signal decides one project per block across all groups. It runs one pooled race.
  • What people see: two workstreams in different groups claim one repo. The Signal page says “Two projects claim this — pick one in Projects.” The block lands nowhere locally (internal/agent/ui/app.js:586).
  • What Atlas already does: it keeps one value per group key, highest confidence first. It also runs the org's repo and workspace rules itself, per group (atlas services/api/app/services/workstream_attribution.py:345-394, 449-479).
  • So Atlas's rule-based numbers are already right. Signal's page is wrong, and Signal's semantic pass under-reports groups.
  • Hypothesis: if Signal decides per group, the page matches Atlas. Each group then gets its own winner, with no extra model work.

Goals

  • G1 — A block lands in every workstream that matches it, in any group, on the page and on the wire.
  • G2 — Nothing is ever dropped for matching twice. “Pick one” goes away.
  • G3 — One group's strong match never hides another group's winner.
  • G4 — A group's total counts each block once. A workstream's total counts each of its blocks in full.
  • G5 — A single-group org gets the same on-device answer it gets today.
  • G6 — Signal's code, local contracts and page say group / workstream / dimension, as Atlas does.

2 · Proposed solution

The model: overlap is allowed, the group counts once

One group, two blocks. Block X matches both Atlas Platform and Signal Client. Block Y matches only Atlas Platform.

RowBlocks countedEst. costHow it is counted
Products (group)X, Y$10distinct blocks · each once
Atlas PlatformX, Y$10every block it holds, in full
Signal ClientX$5every block it holds, in full
Σ workstreams—$15not a total · overlap is $5
  • The group answers “what did this area cost”. Each block once, so it never double counts.
  • A workstream answers “how much work touched this”. Overlap is information, not an error.
  • The page labels it: “Workstreams can share blocks, so they add up to more than the group.”
  • No conflicts to resolve, no precedence to learn, no order to maintain. That is what keeps Signal light.

Signal decides; Atlas does its own thing

  • Signal attributes on the device and sends its answer. Every assigned id goes up in projects, every rule match in project_matches.
  • Atlas is not changed and not waited on. Today it keeps one workstream per group from that answer. Its open work (#246 → #265 → #266) runs its own rules server-side.
  • So Atlas and the Signal page can show different per-workstream numbers for a shared block. That is accepted.

Technical design

  • Group of a workstream: Workstream.Group (today Project.Workstream). Atlas values already get GroupKey(team). Local workstreams use their local group. One with none joins an ungrouped bucket "".
  • Rule pass (step 2): Attribute returns Result{Groups map[string]GroupResult}. Each group lists every workstream id that matched, with its method. The per-group refusal is deleted; no tie-break exists.
  • Semantic pass (step 2): today's rule, run per group. cut_G = max(null_sim, top_G − MARGIN); assign every id at or above it when top_G > null_sim. The verifier halo is around cut_G.
  • Totals (step 3): one Go helper, workstreams.Rollup, over the live rule pass on the same blocks coverage uses — as shipped, so totals, coverage and the Today rows agree by construction (the page already recomputes those live). Group = distinct blocks; workstream = its blocks in full. GET /v1/workstreams returns both for the current week, beside coverage.
  • Sidecar input: each posted workstream carries group. Amended during the build (2026-09-23): a list with no group key at all — an older daemon — is one pooled competition, today's decision, not grouped by team. The fixtures showed why: workstreams the old rule pooled have different teams, so falling back to team would have silently changed an older daemon's answers. The posted list's hash changes once, so workstream documents re-embed once. Message vectors do not.
  • Sidecar output: same shape. Sorted by confidence, fixing the order bug at attrib.go:392. The ledger keeps every id, not just index 0.
  • Wire to Atlas: same keys. Every assigned id. A new model_versions.decision marks the rule.
  • Ledger: the Go side maps each returned id to its group from the list it posted. An id missing from that list is recorded under "".
  • Invariants respected: no text, span or offset crosses (the reflection allowlist is unchanged). Old sidecar gives the old pooled answer, no worse than today. Attribution stays off by default.

Objections

Atlas already puts the block in both groups. Why touch Signal?
True for repo and workspace rules: Atlas re-runs them per group itself. But the Signal page still says “pick one” for a valid setup. And the semantic pass cuts across groups before Atlas ever sees the ids.
Workstream totals add up to more than the group. Isn't that confusing?
It can be, so only the group row is called a total and the overlap is shown as its own line. The alternative is a precedence rule people must learn and maintain. Overlap is the honest answer when two workstreams both describe the work.
Why let Signal diverge from Atlas?
Signal has to stay light: no ordering, no tie-breaks, no conflict UI. It sends what it decided, and Atlas is free to read that however it attributes.
Won't blocks now collect many labels?
More than today, yes: each group applies MARGIN to its own top. Nothing bounds it but MARGIN and the null gate. AC-10 measures it, and the pass stays off by default until it does.
Why not send the group with each id?
It would help a human reading raw rows. But Atlas resolves groups by id, and our key is name-derived. Two keys in two formats would eventually disagree.
Why no schema bump?
No key or vocabulary changes; the list gets shorter. model_versions is an open map built for exactly this marker. A reader can tell old rows from new by decision.
What about blocks already in Atlas?
They keep their pooled answer. Jobs are deleted once published, so there is nothing to replay. Atlas already treats groups as forward-only.
Why rename in the same piece of work? It makes the diff huge.
It does: about 780 Go identifier uses in 104 files, plus 74 Python and UI files. But it lands as its own first commit with no behaviour change, so review stays two small questions. Doing the logic first would mean writing new code in the old words.
Why not rename the wire keys too?
Atlas reads them, and one sits behind a sidecar that updates on its own schedule. Renaming them is an Atlas-first change. Keeping them costs one comment per name.
Single-group orgs pay for this?
No. One group means one race, which is today's race exactly. AC-5 checks the sidecar's answer is unchanged.
