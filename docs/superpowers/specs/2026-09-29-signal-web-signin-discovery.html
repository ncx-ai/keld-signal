Signal Web Sign-in — Discovery

How a person signs in to Signal through the Atlas website, the way Notion's desktop app does it. Sign-in leaves the installers and happens when Signal first opens, with a choice to skip and use Signal locally. This page settles the flow, the security controls and the tests. If it is wrong, we ship a login that leaks a credential or breaks without anyone noticing.

1 · Hypothesis & scope

The why

  • Problem: the installer demands a sign-in with no context, and signing in means copying a code between two windows.
  • Who feels it: every new user, in the installer, before Signal has even opened. #431: "I couldn't proceed without signing in."
  • Business value: install is just install. The first open offers a one-click web sign-in, or local-only use. Fewer installs stall unpaired.
  • Hypothesis: if Signal hands sign-in to the browser and takes the result back itself, a new user pairs without copying anything. The canary proves it daily in dev and prod.

Goals

  • G1 — A person goes from "Log in" to "signed in" without typing or pasting.
  • G2 — No step in the flow lets a credential reach anyone but that person's own Signal.
  • G3 — Every layer is tested automatically: on each pull request, after each deploy, and on a schedule in prod.
  • G4 — The whole flow runs on a laptop against a local Atlas before anything is pushed.
  • G5 — Installers only install. Signal asks on first open, and "use locally only" is a first-class answer.

Explicit exclusions

  • IT-driven rollout with an org enrollment key. That is its own ticket (org enrollment key).
  • Changing tool auto-setup or the page's Integrations view. Tool choice already lives there.
  • Changing what the silent/MDM path does. --code pairs exactly as today.
  • A custom keld:// link type, SSO/SAML, and a server-side logout. See section 3 and section 8.
  • Opening links from inside the desktop app in general. The service opens the browser, so the app needs no change.
  • Per-IP rate limiting on existing setup codes. It is a real gap, logged in section 8, with its own fix.

2 · Proposed solution

How it works, in one picture

  • Signal makes two random secrets and keeps them in memory: a state and a verifier.
  • The browser carries the state there and back. It never carries the verifier.
  • Atlas returns a short-lived code. The code is worthless without the verifier Signal kept.

Technical design

  • Data: no migration. The Redis grant JSON gains an optional challenge. Old grants without it read as "no challenge".
  • Atlas API: POST /api/cli/authorize {redirect_uri, state, code_challenge, code_challenge_method:"S256"} → {redirect_to}. Session-gated, org of the session user. EnrollRequest gains code_verifier?.
  • Atlas web: the authorize page stays behind the login gate, so a signed-out visit keeps its query in next. Continue calls the API and navigates only to the returned redirect_to.
  • Signal: /v1/auth/start stores {state → verifier, api base, expiry} in memory. /auth/callback deletes the entry on first sight, then calls pair().
  • First open: the page shows the choice while unpaired and send_to_atlas is absent. Sign in starts the round trip. Local only writes false through the existing settings route.
  • Installers: macOS drops the pane and its handoff file, and postinstall opens the Signal app. Tools are configured by the daemon's auto-setup, as on every silent install today. Windows swaps onboard.cmd for opening the page, still skipifsilent. install.sh ends with keld signal open. Every --code path is unchanged.
  • Return page: fixed HTML with no values from the URL. The Signal page learns the result from its existing status polling.
  • Invariants respected: the org comes from the Atlas session, never from the request. Send to Atlas off refuses, as /v1/config does (config.go:34-87). Setup codes, --code and keld login stay (AC-12 of the integrations spec).

3 · Alternatives considered

OptionApproachRejected because
AReuse the device flow (keld login): open the approve page, poll until approved.A code approved anywhere is delivered to whoever started it. That is the device-code phishing attack: an attacker far away sends the link, the victim approves, the attacker's machine gets the token. A loopback return can only land on the victim's own machine.
BCustom link type keld://callback.Needs per-OS registration: an app bundle on macOS, a registry entry on Windows, a .desktop file on Linux. On Windows and Linux Signal is a background service with no app to register. Any app can also claim the same link type.
CPut the Signal login token straight in the redirect URL.A long-lived, revoke-only token would sit in browser history and in any proxy log.
DNo challenge/verifier; rely on single use and 120 s.The code rides a URL. A leaked code redeemed first wins the account. The verifier costs one field on each side.
ERedirect automatically, with no Continue click.Then any link opened in a signed-in browser mints a code for whatever listens on 127.0.0.1. On a shared machine that can be another user.
FDo nothing.First sign-in stays "copy a code between two windows". #431 already records that as confusing.

Closest call: option A. It is pure reuse and gives almost the same click path. One fact decided it: a device code works from anywhere, a loopback return works only on the machine that asked.

Test layers — what runs where

  • Layer 1, unit (every PR): the two tables above, the verifier rules, the next case file, the authorize page states.
  • Layer 2, Signal against a fake Atlas (every Signal PR): Playwright drives the real daemon and the mock Atlas. It catches Signal regressions without needing Atlas up.
  • Layer 3, Atlas round trip (every Atlas PR): real Postgres and Redis, no browser. It proves the contract the fake in layer 2 imitates.
  • Layer 4, canary (dev and prod): a real browser and real Atlas, with a small script playing Signal. It runs on a schedule, on demand, and after each dev deploy.
  • Layer 5, shipped binary (after each Signal release): the canary installs the released Signal and signs it in against dev.

Data privacy

  • New PII: none. The Continue screen shows the signed-in user's own email and org.
  • Cross-boundary data: none new. The same two tokens a setup code yields cross the same routes. No prompt text is involved anywhere.
  • Auth surface: /api/cli/authorize is session-gated. /v1/auth/start needs the page secret. /auth/callback needs a live state instead of the secret, which is the one new pattern (section 2).
  • Browser caveat, unverified: Chrome's local-network rules are believed to target sub-requests, not top-level redirects. The canary's Chromium run and one manual Safari and Firefox pass settle it (section 8 #6).

Objections

Why not just auto-open the device flow we already have?
It is closer to reuse, and the clicks are nearly the same. But a device code approved anywhere goes to whoever started it, which is how device-code phishing works. A loopback return only reaches the machine that asked.
Notion doesn't make me click Continue. Why do we?
It is one extra click, true. Without it, any link opened in a signed-in browser would mint a credential for whatever is listening on this computer. The click is what makes "nothing happens unless you meant it" true.
Isn't a verifier overkill for a two-minute, single-use code?
Single use helps, but the first redeemer still wins. The code travels in a URL, and URLs end up in history and logs. The verifier costs one field on each side and makes a leaked code worthless.
Why fix the next bug in this piece of work?
It predates this work. But every new Signal user will now pass through /login?next= from a link. Shipping a new front door through a known bypass would be careless.
The canary mints a live token every six hours. Isn't that a mess?
Yes, the rows pile up, and Atlas has no revoke today. They belong to a canary-only account and are stored hashed. The revoke route in section 8 #2 cleans this up and also fixes logout.
If the installer stops asking, won't fewer people sign in?
Some will choose local only, and that is a real answer, not a failure. Today's forced prompt did not make people sign in; it stopped some of them installing. Sign in stays one click away in Settings, and admins see unpaired machines in the fleet view.
Five test layers sounds heavy. Which one could we drop?
Layers 1 and 3 mostly extend jobs that already run. Layer 2 is the only new Signal CI job. Layer 5 is the only test of the binary people actually install, so it is the last one to cut.
