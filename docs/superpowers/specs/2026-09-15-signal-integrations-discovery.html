Signal Integrations — Discovery

An Integrations pane that lists every tool Signal knows, says how each is wired, shows whether it is working, sets up a tool that appears later, reports a break to us, and a conformance matrix that proves each integration against the latest tool version whenever a tool or Signal releases. If this is wrong, Codex stays silently spend-only and the next Codex release breaks Claude-shaped assumptions with nobody told.

1 · Hypothesis & scope

The why

  • Problem: A tool installed after Signal is never configured. A configured tool that stops producing is reported nowhere. Codex has produced no classified prompt since it was wired, and nothing said so.
  • Who feels it: The user, who sees a tool "set up" and nothing in Atlas. Us, who learn a tool release broke capture only when a customer asks.
  • Business value: One person can support many tools: the machine sets them up, the machine says which lane broke, the matrix says which tool version broke it.
  • Hypothesis: If integration state is one computed fact per tool and surface, shown in the pane, in doctor and in a fleet event, then a break is visible within a day on the machine and within a day across the fleet, and adding a tool costs one adapter plus one conformance scenario.

Goals

  • G1 — A user sees every known integration, how it is wired, and whether it works, in the local UI.
  • G2 — A tool installed later is configured without a command, with a backup, and the pane says so.
  • G3 — A broken integration reaches us as an event with the tool version attached, and the user can send a redacted report with one click.
  • G4 — Each integration is proven against the latest tool version: on Linux whenever a tool publishes a new version, on three OSes whenever Signal releases, and on demand. Never on a timer alone. A mock model is used where the tool accepts one; a real provider credential is used where it does not. Lack of a credential never excludes a tool.

Explicit exclusions

  • The Codex and Pi readers. Codex has its own discovery; Pi is listed as unsupported until a reader exists. This page makes both visible, not working.
  • Antigravity, Cursor, and a browser extension. They appear as catalogue rows only, with their storage class named.
  • Any Atlas UI. Atlas already receives client-events; a fleet dashboard over integration.* is Atlas work.
  • Testing provider behaviour. The matrix tests our capture, not the model. Credentials are provided where a tool needs one (Gabriel, 2026-09-15); they are a CI secret, not a reason to skip a tool.
  • Auto-updating the tools themselves.
  • Driving the native installer wizards with GUI automation (AppleScript, pywinauto). The silent paths run the same code; the one GUI-only claim, "the onboarding window opens after the package finishes", stays a manual check per release.

Technical design

  • Data: No store schema change. New file ~/.keld/state/integrations.json: last-seen per source × surface, last emitted state per source. New setting auto_setup_integrations (default true) in agent-config.json. New dir ~/.keld/reports/.
  • Catalogue: one Go table: id, display name, config dir, surfaces with kind and documented flag, storage class (jsonl-tail / db-poll / rpc), support level (supported / unsupported), and the expected lanes for that support level. A lane a tool cannot yet feed is not expected, so it cannot make the tool broken: Codex expects hook + otel until its reader ships, then watcher + reader join. Without this, Codex would read broken · reader by construction from day one. Claude Code, Codex, Gemini CLI, Cowork supported; Pi, Antigravity, Cursor unsupported rows.
  • Wiring facts (read back from disk every detector poll, never from memory): the tool's config parses and contains what the adapter would write (the existing drift check in status.go); the telemetry endpoint points at the proxy port; for Codex, a hooks.state entry exists for keld's hook source; the newest tool session started after the config's mtime. Each becomes a tick or a waiting_on reason on the row. This is the answer to "is my setup correct" that needs no activity at all.
  • Lane facts: hook lane = last pointer with Origin: hook per source; watcher lane = last pointer with Origin: watcher; otel lane = teleproxy last forward per source; reader lane = store rows exist for the last N pointers of that source. Tool session start comes from the newest transcript mtime and its first timestamped line.
  • API: GET /v1/integrations; POST /v1/integrations/{id}/setup → runs the adapter, returns {backup, restart_required}; POST /v1/integrations/{id}/report → returns {report_path, event_queued}. Loopback, existing secret.
  • Read path: pane polls /v1/integrations every 10 s like the health dot; doctor calls Compute once.
  • Conformance: per tool a scenario file: install command, config-dir env for isolation (CLAUDE_CONFIG_DIR, CODEX_HOME, PI_CODING_AGENT_DIR or HOME), headless command, mock-model env (ANTHROPIC_BASE_URL, model_providers, registerProvider), and the five checkpoints read from the isolated daemon's /v1/integrations, store and mock Atlas.
  • Invariants respected: no text in any event or report (redaction gate, AC-6); the pane never triggers a model load; a tool config is edited only through the adapter with a backup; the daemon never edits a config while the manifest already records that tool.
  • Installer rule (AC-12): every installer ships with a silent mode, and every onboarding step has a command equivalent. This is what lets the matrix run the REAL installer on a clean VM, and it is also what an MDM rollout needs. Playwright covers the Signal page only; it cannot drive Apple's Installer wizard, Inno's pages or a native Tauri window, so an onboarding step that exists only as a window is untestable and undeployable at scale. The wizards are shells around the same steps; the silent path runs the same code without the clicks.

System diagram

Conformance matrix — how it runs on GitHub

One workflow, .github/workflows/conformance.yml, beside the existing installers.yml. It runs when a tool publishes a new version (Linux only, since a transcript shape is the same on every OS), when Signal releases (all three OSes, because installers and service registration are OS-specific), and on demand. There is no nightly full run: the cost went to the wrong place, and a run with nothing new to test proves nothing new. One job per OS × scenario. Every job installs the tool at @latest, installs Signal unattended (AC-12), talks to a mock model and a mock Atlas, and reads five checkpoints from the isolated daemon. No provider account is used by default; a real key is a CI secret added per tool only where the mock cannot stand in.

Against the plan's included minutes (Team: 3,000/month) a Windows minute counts 2× and a macOS minute 10×. At two tool releases a week and two Signal releases a month that is about $8/month, against $105 for a nightly full matrix. A self-hosted Mac makes the macOS leg free (the platform charge for self-hosted runners was postponed).

Two chains on one VM, with a random split of the tools

One job is one VM running a chain of steps, each step asserting its own checkpoints. The supported, installable tools (today Claude Code, Codex, Gemini CLI, Pi) are split at random into a before half and an after half, so every run covers both "tools first" and "Signal first" and the pairing changes each time. The seed is the run id, printed in the summary and in any issue, and accepted as a workflow_dispatch input so a failure reproduces exactly.

  • Per run: a tool release runs chain A on Linux twice, once with the released tool in before and once in after, the split of the others random. A Signal release runs chains A and B on all three OSes.
  • A failing step stops its chain and the summary names the step, the seed, the tool and the checkpoint; the issue title carries the same. Later steps are marked skipped, not failed, so one break reads as one break.
  • Why chaining is right here: a user's machine is a chain too. A leftover from an earlier step that breaks a later one is a real bug, and the per-step checkpoints say which step introduced it.
  • Unit-tested instead, on every pull request: a tool already running when setup runs (restart_required, never broken); a tool that already has its own telemetry section (skip or replace); uninstall restores every backup. Each is a decision in our Go code and a fake filesystem proves it in milliseconds.
  • Local reproduction: make conformance TOOL=<tool> runs the same script on a laptop; on Linux through the same Compose file the ubuntu job uses. macOS runs natively on the developer's machine; Windows is the runner or a local VM.
  • Mock model by default, real key by exception. The mock is deterministic and free, and a failure against it points at our capture. A real provider is used only where a tool cannot be pointed at a mock; today that is Gemini, and its key is a CI secret. Credentials never exclude a tool (G4).

3 · Alternatives considered

OptionApproachRejected because
ADoctor CLI only, no pane, no detectorDoctor already exists and was clean during 40 minutes of dead telemetry. Nobody runs it unprompted; a tool installed later stays unconfigured forever.
BFleet view in Atlas onlyThe facts live on the machine: config dirs, hook arrivals, tool versions. Atlas sees only what is forwarded, so it cannot tell "not configured" from "quiet". The events this page adds are what would feed that view later.
CConformance with real provider accountsSecrets in CI, spend per run, and a run that fails when a provider is down rather than when we broke. The mock path is verified for Claude Code today; real-credential runs stay optional where the mock is unverified.
DPrompt the user before configuring a newly installed toolThe installer already edits the same files with one consent and a backup. A prompt nobody sees is a tool that stays unconfigured. Kept as the off position of one toggle.
EOwn VMs per OS (Tart, UTM) instead of GitHub runnersThe installer workflow already runs on macos-14 and windows-latest and installs tools there. VMs become necessary only when a tool cannot be installed on a runner (section 8).
FDo nothingCodex stays spend-only with no signal, Pi appears nowhere, and the next tool release is found by a customer.

Closest call: D. It costs one prompt. It lost on the measured pattern that a notice nobody is looking at is a notice that did not happen; the toggle keeps the choice available.

Data privacy

  • New PII: None. The report bundle holds versions, counters, states and redacted log lines. The redaction gate that already strips paths and reduces errors runs on every field; AC-6 plants a prompt and a key and asserts absence.
  • Cross-boundary data: tool version strings and lane states leave the machine in events. No text, span, offset or path.
  • Auth surface: none new. The routes ride the loopback secret; the events ride the ingest token.

Objections

Doctor already reports problems. Why a pane?
Doctor is correct and unread. It said "No problems found" through 40 minutes of dead telemetry because every fact it could reach was fine, and nobody ran it anyway. The pane is open when the user looks at Signal, and the detector acts without either.
Editing a user's tool settings from a background service is a step too far.
It is the same edit the installer makes, with the same backup, after the same consent. The difference is timing. The toggle exists for anyone who wants the prompt back, and the pane shows the backup path for every edit.
Testing against a fake model proves nothing about the real provider.
True, and that is not what it tests. It tests that the tool at its latest version still writes the files, fires the hooks and emits the telemetry our capture depends on. That is the part that broke three times this year. Provider behaviour is the tool's problem, and an optional weekly real-credential run covers it where it matters.
This is a lot of surface for a one-person team.
It is the surface that lets one person stay one person. Every piece reuses something that exists: adapters, manifest, doctor states, client-events, the isolated daemon, the CI runners. The new code is one state function, one pane, one mock server and one workflow.
Why not fix Codex first and do this later?
Fixing Codex without this repeats the failure: nothing would say when the next release breaks it. AC-9 is in this page precisely so the pane has a second working tool to show, and so the Codex scenario in the matrix guards the fix.
Twenty-four hours is arbitrary.
Yes, and it is labelled as a starting guess. The right window depends on how quiet real machines get, which the fleet events will show within a week. Idle-is-not-broken keeps a wrong window from producing false alarms while it is tuned.
