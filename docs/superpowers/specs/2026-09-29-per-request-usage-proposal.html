Counting tokens per request

Signal's page counts tokens and spend from 20-minute blocks, with one model per block. This proposes counting them request by request, from the reader Signal already runs, and keeping blocks for what they are good at: what the work was about.

1 · Today — exact per-request data passes through, and only block totals are kept

Two readers look at the same transcript. The transcript reader sees every request with its model and tokens, deduplicated, and sends them to Atlas. The analysis engine sums a block's tokens and names one model for it. Only the second reaches the page.

2 · Why it breaks — one model per block, and nothing until the block closes

A block is priced as if every request in it used the block's main model. It also reaches the page only when it closes, up to 20 minutes after the work, or 15 minutes of silence. The timeline shows an illustrative block: ten requests, two models.

The same shape produced the "no model" rows: in three Codex blocks this week the engine saw no model at all, because it counts a model only on an assistant message and those blocks had none it could use. The request records name gpt-6-astra the whole time.

3 · The fix — three things change

  1. The reader keeps what it reads. Each request goes into a new ledger table, keyed on its request id, as it is read. It is the same deduplicated record Atlas already gets.
  2. Every request row is kept for good. No rollup table and no pruning. The page sums the rows it needs, and a duplicate is caught however old it is.
  3. The page reads usage from that table. Tokens, spend and "By model" come from requests. "By repo", "By project" and the activity grid still come from blocks, joined by session and time.

Schema — one additive table in ledger.db

TableColumnsRule
requestssource, session, request_id (PK) · ts · model · input, output, cache_read, cache_creation · estimate_usdOne row per request. Insert-or-ignore on the key, so a re-read cannot add twice. Never pruned. Indexed on ts for range reads.

Additive only. An older Signal on the same machine ignores the table. Nothing existing is altered or migrated.

Over months and years — what is kept, and for how long

  • Transcripts deleted later: nothing is lost. Today your ledger already holds 291 Claude Code blocks whose transcripts Claude Code has deleted.
  • What is lost: a transcript deleted before Signal read it. The daemon resumes from its saved position after a restart, so this only happens if it is off for longer than Claude Code keeps transcripts — 30 days.
  • History before this ships: the first time the new version starts, it reads every transcript still on disk once and counts it. That is the last 30 days of Claude Code and all your Codex rollouts, back to Sep 2025. Days older than that show no usage on the Overview (D2), with a note saying where each tool's data starts.
  • No overload: the page only asks for its range, read through an index on time: 30 days is about 36,000 requests here, sent as ~4,400 five-minute sums. The table grows by ~130 MB a year at your rate (measured), and keld signal doctor reports its size. At ten times your rate for three years a month still reads in 731 ms, so a rollup waits until reads slow, not until a size.

Objections

Why not fix the analysis engine to count models per request instead?
It would work, and the engine already stores tokens per request. But it does not store the model per request, so it needs an engine release and a re-read of every transcript. The daemon's reader already produces the exact record, and Atlas already trusts it.
Won't this disagree with Atlas?
Less than today. Atlas prices from the same request records this reader sends. The page and Atlas count the same requests; only the rates can differ, which the page already says with "est.".
Another table is another thing to break.
True, so it is one table, additive and ignored by older builds. The tests that guard it are the same dedupe rules the Atlas feed already depends on.
What if the laptop is off for a month?
Signal resumes from where it stopped. It loses only transcripts Claude Code deleted in the meantime — its 30-day cleanup. That is true today for blocks too.
Why not roll old rows up to save space?
A rollup would save space, but it adds a second table to keep in sync and a pruning job. That only earns its place if space or speed is a real problem. Measured, the table is ~130 MB a year at your rate and a month reads in under a second even at ten times that, so the rollup waits until reads slow.
Why keep blocks at all?
Tokens do not need them. "What was this work about" does: repo, project, and the activity grid are properties of a stretch of work, not of a single request. The join gives both.

Each point below is its own entry, so it can be discussed on its own. The first two are decisions; the rest are risks to settle before building.

D1 · Decided — Focus blocks rows will not add up exactly to its Tokens and Est. spend tiles
The Focus blocks pane has four tiles at the top. Two of them, Tokens and Est. spend, switch to request totals, the same numbers the Overview shows (T14). The other two, Focus blocks and Focus time, are about blocks and stay as they are. Each block row in the list below keeps its own block total. The same holds for the Overview's histogram: its squares are blocks, and under Tokens their shade comes from each block's total, so it stays block-based too. The Focus blocks pane's Rhythm strip carries no token counts and is unaffected. Work still in progress, and requests at a block's edge, land differently, so the rows and the tiles can differ slightly. Decided 2026-09-29 (Gabriel): accept it for now. The Focus blocks pane will likely be redesigned or removed, so moving its rows to request totals would be work thrown away. Still open: whether the new design keeps the Overview histogram on block totals or moves its shading to requests. A side effect of D2: the 291 Claude Code blocks from before 28 Aug still appear on block-based views (the Focus blocks list, the Overview histogram) while the Overview's usage shows nothing for those days.
D2 · Decided — the Overview shows only what the new table holds; days with no transcript left show nothing
Every transcript still on disk is counted: the first time the new version starts, it reads each one once and fills the table. No reinstall is needed. On this Mac that is the last 30 days of Claude Code (oldest on disk: 28 Aug) and all your Codex rollouts, back to Sep 2025. D2 is only about days whose transcripts are already gone — mainly the 291 Claude Code blocks from before 28 Aug. With no file left there is nothing to rebuild requests from. Decided 2026-09-29 (Gabriel): the Overview's tokens, spend and "By model" come only from the new requests table. Days with no transcript on disk show no usage — no block fallback, no partial backfill. Simpler, and fine for an alpha. Because tools keep their files for different lengths, the Overview says where each tool's data starts, so a drop at 28 Aug does not read as a real change in usage.
R1 · Note (downgraded after review) — keys are stable and re-reads are rare
Claude Code writes a request id; Codex and Gemini have stable keys in Signal's reader too — Codex: session @ record timestamp # position in the file; Gemini: each response's own message id. The content fingerprint is Atlas's, over the fields Signal sends; Signal hashes nothing, and duplicates at Atlas are Atlas's to handle. For the page, a key only matters when a file is read again, and in normal running none is: the daemon resumes each file from its saved position, including across a new version. Gemini re-parses a rewritten session file, but its own message ids make the old responses add nothing.

The one real case, found in review: read positions live in ~/.keld/watch and the ledger in ~/.keld/state, so either can be lost without the other (uninstall removes state wholesale). Positions lost, ledger kept: files are re-read, and stable keys make that add nothing — T4 and T6 guard it. Ledger lost, positions kept: nothing is re-read and history would silently go missing. Design: tie the first-start backfill to the table itself (a marker in ledger.db), not to the read positions, so an empty table always refills from what is on disk.
R2 · Accepted — the reader runs only for tools whose own telemetry is off
That is deliberate for Atlas: counting both would double count there. The local count must run for every tool regardless of that setting, or a machine with a tool's own telemetry on shows nothing for it. Mitigation: separate the local write from the Atlas switch, with its own test. Accepted 2026-09-29 (Gabriel).
R3 · Accepted — the first start reads every transcript still on disk
On this Mac that includes Codex history back to Sep 2025. Read all at once, it keeps the laptop busy on first start. Mitigation: pace it the way the existing first-read backfill is paced, a few files per poll. Accepted 2026-09-29 (Gabriel).
R4 · Accepted — "By repo" and "By project" stay slightly less complete than the total
Those splits come from blocks, joined by session and time. A request outside any block lands in "no repository" or "no project". Proposed: accept it, since the total and "By model" stay exact. Accepted 2026-09-29 (Gabriel).
N1 · Note — the planned engine fix for Codex models is no longer needed
With the model split taken from requests, the analysis engine no longer has to see a model in every block. Proposed: drop that change rather than do it next.
